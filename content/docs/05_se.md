## Basics

### Origins, project & process
- **Software engineering** term was popularized at the **1968 NATO conference**.
- **Brooks's Law** (Fred Brooks, *The Mythical Man-Month*): adding people to a late project makes it later.
- **Iron triangle** = **scope, time and cost** (quality in the center).
- **CMMI Level 5** = **Optimizing** (1 Initial, 2 Managed, 3 Defined, 4 Quantitatively Managed).
- **SDLC phases:** Requirements → Design → **Implementation (coding = writing the source code)** → Testing → Deployment → Operations → Maintenance.
- **Maintenance types:** **Corrective** (fix bugs after release) · **Adaptive** (new environment, e.g. new OS) · **Perfective** (add features / improve performance) · **Preventive** (refactor to avoid future problems).

### SDLC models & Agile
| Model | Remember |
|---|---|
| **Waterfall** | oldest, **linear sequential**, rigid; each phase ends before the next |
| **V-Model** | each development phase **paired with a testing phase** |
| **Incremental** | delivered in **successive small portions**, each adding functionality |
| **Spiral** | risk-driven (Boehm); Planning, Risk Analysis, Engineering, Evaluation |
| **Agile** | iterative, stakeholder-driven, frequent delivery, welcomes change |
- **Agile Manifesto** values: **Working software** over comprehensive documentation · Individuals and interactions over processes and tools · Customer collaboration over contract negotiation · Responding to change over following a plan.
- **Scrum roles:** **Product Owner** (maximizes product value, manages the backlog) · **Scrum Master** (helps team follow Scrum, removes impediments) · **Developers**.
- **Scrum events:** **Sprint** (fixed-length iteration that produces a usable Increment) · Sprint Planning · **Daily Scrum = 15 minutes** · **Sprint Review** (end of Sprint, inspect the Increment with stakeholders) · Sprint Retrospective.
- **Scrum artifacts:** **Product Backlog** (everything that might be needed in the product) · Sprint Backlog · Increment.
- **Kanban** = visual board (To Do / Doing / Done) with **WIP limits**. **XP (Extreme Programming)** = **pair programming, TDD, small releases**, CI, refactoring.
- **Git** = distributed version control system, created by **Linus Torvalds** (2005).

### Requirements
- A good requirement says **what, not how**; mandatory items use the word **"shall"**.
- **Functional requirement (FR)** = what the system does (*"the system shall allow users to log in"*). **Non-functional (NFR)** = quality/constraint (*"respond within 2 seconds"*).
- **SRS** = **Software Requirements Specification**.
- **Ishikawa (fishbone)** diagram = cause-and-effect analysis.
- **MoSCoW** = **Must, Should, Could, Won't**.

### Testing & quality
- **Testing levels (in order):** **Unit** (functions/components in isolation) → Integration → System → **Acceptance** (users/customers confirm it meets their needs).
- **Black-box** = no knowledge of internal code. **White-box** = examines internal code structure.
- **Regression testing** = re-check that recent changes did not break existing features.
- **TDD cycle:** **Red → Green → Refactor**.
- **Verification** = "Are we building the product **right**?" · **Validation** = "Are we building the **right** product?"
- **COCOMO** (Barry Boehm) = software cost estimation model.

### UML
- **UML** = **Unified Modeling Language**. **Structural** diagrams: **Class**, Object, Package, Component, Deployment. **Behavioral**: Use case, Sequence, Activity, State.
- **Class diagram visibility:** **+ public · − private · # protected** · ~ package · / derived.
- **Relationships:** **Generalization** = inheritance (solid line, **hollow triangle**) · **Aggregation** = **hollow diamond** (parts can exist alone) · **Composition** = **filled diamond** (part cannot exist without whole).
- **Use case diagram** = actors and the functions the system gives them. `«include»` = included use case is **always required**; `«extend»` = optional.
- **Sequence diagram** = messages between **lifelines** along a vertical time axis.
- **Activity diagram** = workflow with decisions, **fork/join bars** and swimlanes.

### Design patterns, SOLID, MVC & licenses
- **Gang of Four (GoF)** book describes **23** design patterns.
- **Observer** = notifies dependent objects when an object's state changes (behavioral). **Singleton** = only one instance of a class (**creational**).
- **SOLID:** **S** = Single Responsibility · **O** = **Open/Closed** · L = Liskov Substitution · I = Interface Segregation · D = Dependency Inversion.
- **MVC** = **Model–View–Controller**; the **Model** manages data and business logic.
- **GPL** = **copyleft** license: derivative works must also be open source (BSD/MIT are non-reciprocal).

## Fundamentals & standards · finals
- **Software engineering** = systematic, disciplined, quantifiable approach to development, operation and maintenance of software (IEEE). Term popularized at the **1968 NATO conference** (Garmisch).
- **Software crisis** (1960s): late, over budget, buggy. **Brooks's Law** (Fred Brooks, *The Mythical Man-Month*): adding people to a late project makes it later. **"No Silver Bullet"** (Brooks 1986). **Conway's Law**: system design mirrors the org's communication structure.
- Software characteristics: not manufactured (developed), doesn't "wear out" but **deteriorates** through change; mostly custom-built.
- Types: system, application, engineering/scientific, embedded, web apps/mobile apps, AI software, product-line.
- **Project** = temporary endeavor to produce a unique product/service. Sources of projects (coach): **Problem · Opportunity · Directive**.
- **Quality triangle / iron triangle:** scope, time, cost (quality in center).
- Standards: **IEEE**, **ISO/IEC 12207** (software life cycle processes), **ISO 9001** (QMS), **ISO/IEC 25010** (product quality), **ISO/IEC 27001** (info security), **CMMI** levels: 1 Initial · 2 Managed · 3 Defined · 4 Quantitatively Managed · 5 Optimizing. **PMBOK** (PMI), **PRINCE2**, **SWEBOK**, **BABOK** (business analysis).

## SDLC & methodologies
- Coach's definition: systems approach, **multistep, iterative, methodical**; turns a newly developed project into an operational one; both technical and non-technical.
- **Phases (cycle):** **Requirements → Design → Implementation → Testing → Deployment → Operations → Maintenance** (maintenance includes development/implementation/support). Alternative textbook: Planning → Analysis → Design → Implementation (Coding) → Testing → Deployment → Maintenance.
- **Maintenance types:** *Corrective* (fix bugs) · *Adaptive* (new environment) · *Perfective* (enhance/performance) · *Preventive* (refactor to avoid future issues). Typically 60–70 % of cost is maintenance.

### Methodologies (coach's list)
| Model | Key idea |
|---|---|
| **Waterfall** | **Linear sequential**, oldest; each phase finishes before next; rigid, requires all requirements defined before design; fully documented; used by **government contractors**; no going back |
| **V-Model** | Waterfall bent into a V; each development phase paired with a **testing phase** (verification on left, validation on right) |
| **Iterative** | Waterfall delivered as **mini-projects**; **Rational Unified Process (RUP)**; good for large projects, highly customized products, incorporating user feedback |
| **Incremental** | Build in pieces; each increment adds functionality |
| **Spiral** | Boehm; four quadrants repeating: **Planning → Risk Analysis → Engineering → Evaluation**; risk-driven |
| **Prototyping** | Build a model first for feedback; types: **Rapid throwaway, Evolutionary, Incremental, Extreme** |
| **Big Bang** | Little/no planning; coding first; for tiny/experimental projects |
| **RAD** | Rapid Application Development; minimal planning, fast prototypes |
| **DevOps** | Dev + Ops collaboration; automation, CI/CD, flexible resources |
| **Agile** | Iterative & stakeholder-driven; **"fast failure" is good**; meets stakeholder expectations; frequent delivery |
- **How to recognize an effective SDLC:** meets stakeholder expectations, finishes within time & cost, system maintainable throughout life.

### Agile in depth
- **Agile Manifesto (2001)** – 4 values: **Individuals and interactions** over processes and tools · **Working software** over comprehensive documentation · **Customer collaboration** over contract negotiation · **Responding to change** over following a plan. (12 principles.)
- **Scrum:** Roles: **Product Owner, Scrum Master, Developers** (team). Events: **Sprint** (≤ 1 month), **Sprint Planning, Daily Scrum (15 min), Sprint Review, Sprint Retrospective**. Artifacts: **Product Backlog, Sprint Backlog, Increment**. Concepts: user stories ("As a… I want… so that…"), story points, velocity, burndown chart, Definition of Done.
- **Kanban:** visual board (To Do / Doing / Done), WIP limits, continuous flow (Toyota origin). **XP (Extreme Programming):** pair programming, TDD, CI, refactoring, small releases (Kent Beck). **Lean:** eliminate waste. **SAFe** scaling.
- **DevOps / CI/CD:** *Continuous Integration* (merge & test often), *Continuous Delivery* (always releasable), *Continuous Deployment* (auto-release). Tools: Git, GitHub/GitLab, Jenkins, GitHub Actions, Docker, Kubernetes, Terraform, Ansible. **Infrastructure as Code**.
- **Git:** `init, clone, add, commit, status, log, diff, branch, checkout/switch, merge, rebase, pull, push, fetch, stash, tag, reset, revert`. Created by **Linus Torvalds (2005)**. GitHub (Microsoft acquired 2018). **Pull request** = request to merge.

## Requirements engineering
- **Characteristics of a good requirement:** describes **what, not how**; atomic; unique; documented & accessible; identifies owner; approved; **traceable**; necessary; complete; unambiguous; **quantitative & testable**; identifies applicable states; uses **"shall"** for mandatory, "should", "will"; avoid words like *optimize, maximize, minimize*.
- **Requirements cycle:** raw requirement → organized → analyzed → complete requirement → **specifications**. Phases: **Elicitation → Organization → Analysis → Prototype → Specification/Documentation**.
- **Elicitation questions (5W1H):** Who, What, Where, When, How, Why.
- **Fact-finding techniques:** **sampling, research & site visiting, observation, questionnaires, interviews, system prototyping, Joint Requirement Planning (JRP)/JAD**.
- **Functional requirements (FR)**: what the system should do – inputs accepted, outputs produced, data stored, computations, timing/synchronization. **Non-functional (NFR)** – global constraints/qualities: *interface, performance (response time, throughput), security (user roles, survivability), operating (physical constraints, personnel skill, maintenance access), lifecycle (maintainability, portability), economic, development limits (time, resources, standards)*. NFRs are hard to model, informally stated, contradictory, hard to enforce/evaluate.
- **User requirements** = natural-language statements + diagrams of services and constraints (customer-level). **System requirements** = detailed description of all services (contract between client and contractor). **URS/URD** = User Requirement Specification; **SRS** = Software/System Requirement Specification (IEEE 830 / **ISO/IEC/IEEE 29148**).
- **Tools:** affinity diagrams, force-field analysis, **Ishikawa fishbone (cause-and-effect)**, Pareto diagrams (80/20), Pugh charts, QFD. **Cause-and-effect analysis steps:** identify problem → work out major factors → identify possible causes → analyze diagram.
- Other: MoSCoW prioritization (Must, Should, Could, Won't), use cases, user stories, traceability matrix, feasibility study (technical, economic, operational, legal, schedule — TELOS), SWOT, cost–benefit analysis, ROI, payback period.
- **Design Thinking approach:** Empathize → Define → Ideate → Prototype → Test.

## ISO/IEC 25010 quality · finals
- Part of **ISO/IEC 25000 series = SQuaRE** (Systems and software Quality Requirements and Evaluation); replaces ISO/IEC 9126 (quality model) and 14598 (evaluation process). Divisions: **2500n** Quality Management · **2501n** Quality Model · **2502n** Quality Measurement · **2503n** Quality Requirements · **2504n** Quality Evaluation.
- **Coach's (2023) 9 characteristics:** 
  1. **Functional Suitability** – completeness, correctness, appropriateness.
  2. **Performance Efficiency** – time behaviour, resource utilization, capacity.
  3. **Compatibility** – co-existence, interoperability.
  4. **Interaction Capability** (formerly *Usability*) – appropriateness recognizability, learnability, operability, user error protection, user engagement, inclusivity, user assistance, self-descriptiveness.
  5. **Reliability** – faultlessness, availability, fault tolerance, recoverability.
  6. **Security** – confidentiality, integrity, non-repudiation, accountability, authenticity, resistance.
  7. **Maintainability** – modularity, reusability, analysability, modifiability, testability.
  8. **Flexibility** (formerly *Portability*) – adaptability, scalability, installability, replaceability.
  9. **Safety** (new in 2023) – operational constraint, risk identification, fail safe, hazard warning, safe integration.
- *Older 2011 edition (8 characteristics):* Functional suitability, Performance efficiency, Compatibility, **Usability**, Reliability, Security, Maintainability, **Portability**.
- Also: *quality in use* model (effectiveness, efficiency, satisfaction, freedom from risk, context coverage). **Verification** = "Are we building the product right?" **Validation** = "Are we building the right product?"

## Testing & quality assurance
- **Testing levels:** **Unit → Integration → System → Acceptance (UAT)**. **Alpha** (in-house) vs **Beta** (real users).
- **Approaches:** **Black-box** (no code knowledge; equivalence partitioning, boundary-value analysis, decision tables), **White-box/glass-box** (statement/branch/path coverage, cyclomatic complexity – McCabe), **Grey-box**.
- Types: functional, regression, smoke (build sanity), sanity, performance (load, stress, spike, endurance), security (pen test), usability, compatibility, exploratory, A/B, mutation, fuzz.
- **Integration approaches:** big-bang, top-down (stubs), bottom-up (drivers), sandwich. **Stub** = fake called module; **driver** = fake caller.
- **TDD** (Red → Green → Refactor). **BDD** (Given/When/Then, Cucumber). Frameworks: JUnit, pytest, Jest, Selenium, Postman, Cypress.
- **QA vs QC:** QA process-oriented (prevent defects); QC product-oriented (detect defects). **Defect vs bug vs failure vs error**: error (human mistake) → fault/defect/bug (in code) → failure (observed wrong behaviour).
- **Code review, static analysis, inspection, walkthrough**. Metrics: LOC, cyclomatic complexity, defect density, code coverage, MTBF/MTTR.
- **Estimation:** **COCOMO** (Boehm), **Function Points**, Use-case points, Planning Poker. **Project scheduling:** **Gantt chart**, **PERT** (3-point: (O + 4M + P)/6), **CPM** (critical path), **WBS**.
- **Risk management:** identify → analyze → plan → monitor (risk matrix; mitigate, avoid, transfer, accept). **Configuration management / version control / change control board**.

## System modeling & DFD
- **System model** = abstract view of a system. Natural language for requirements; **graphical notation based on UML** (Unified Modeling Language). Uses: facilitate discussion, document existing system, detailed description for generating implementation.
- **Perspectives:** **External** (context/environment) · **Interaction** (system ↔ environment or between components) · **Structural** (organization/data structure) · **Behavioral** (dynamic behavior).
- **Classification of models:** *Context model* (system boundaries) · *Interaction model* (use case, sequence; user–system, system–system, component) · *Structural model* (class diagram, ER diagram) · *Behavioral model* (data-driven → DFD/activity; event-driven → state machine).
- **System boundaries** define what's inside/outside; "political judgment".
- **DFD (Data Flow Diagram):** shows information flow; physical (how) or logical (what); levels: **Level 0 = context diagram** (single process + external entities), **Level 1** (major sub-processes + data stores), **Level 2+** (further decomposition). Symbols: external entity (square), process (circle/rounded), data store (open rectangle/two lines), data flow (arrow). Rules: no data store-to-store directly, processes need input & output (no miracles/black holes).
- **Behavioral:** data-driven (activity model e.g., insulin pump), event-driven (**state machine**: states = nodes, events = arcs; e.g., microwave oven: Waiting → Checking → Cook → Done; Disabled; Alarm).
- Why model: "we build models so we can better understand the system we're developing"; we can't understand complex systems in entirety. Tools: draw.io, Lucidchart, StarUML, Visual Paradigm, PlantUML, Mermaid, Figma, Miro.

## UML
- Created by **"The Three Amigos": Grady Booch, Ivar Jacobson, James Rumbaugh**; standardized by the **Object Management Group (OMG)**. UML 2.x has 14 diagram types: **7 structural** + **7 behavioral**.
- **Structural:** Class · Object · Package · Component · Composite structure · Deployment · Profile.
- **Behavioral:** Use case · Sequence · Activity · State (state machine) · Communication · Timing · Interaction overview. (Sequence/communication/timing/interaction overview = *interaction* diagrams.)

### Class diagram
- Three compartments: **Name · Attributes · Operations**. Visibility: **+ public, − private, # protected, ~ package, / derived** (e.g., `/age`).
- Active class (initiates/controls activity) vs passive class (stores data).
- **Relationships:** 
  - **Association** (static relationship; "has/enrolled in"). 
  - **Multiplicity:** `1`, `0..1`, `*`/`0..*`, `1..*`, `n`.
  - **Generalization** (inheritance, "is-a"; hollow triangle arrow; e.g., Employee → Part-time/Full-time).
  - **Aggregation** ("has-a", parts can exist independently; **hollow diamond**; e.g., apartment–rentee).
  - **Composition** (strong ownership, part can't exist without whole; **filled diamond**; e.g., hotel building–floor).
  - **Dependency** (dashed arrow; change in one may affect the other, not vice versa; e.g., Order depends on Product).
  - **Realization** (dashed with hollow triangle → implements interface).
- **Object diagram** = instance snapshot at a moment (`Student101: Student`, attribute values); verifies the class diagram.
- **Package diagram:** groups classes; dependencies **«import»** (functionality added to target package) and **«access»** (source available to target).
- **Component diagram:** modular replaceable parts; symbols: component, **provided interface (lollipop)**, **required interface (socket)**, **port** (square on edge).
- **Deployment diagram:** nodes (hardware) and artifacts.

### Behavioral
- **Use case diagram:** **actors** (stick figures; users/external systems), **use cases** (ovals), **system boundary** (rectangle), relationships. `«include»` = included use case is *required* to perform the base use case (always). `«extend»` = optional/conditional extension of the base use case.
- **Sequence diagram:** vertical **time axis**, **lifelines** (participants), **activation bars** (duration of operation), messages: call (solid), return (dashed), self, recursive, create, destroy; **combined fragments** (operators: `alt`, `opt`, `loop`, `par`, `break`, `ref`).
- **Activity diagram:** workflow; start (filled circle), action nodes, decision (diamond), fork/join bars, end (bullseye), swimlanes.
- **State diagram:** states, transitions, initial & final states, events/guards/actions.
- **ERD** (Chen notation / crow's foot) belongs to structural/data modeling → `09`.

## Architecture & APIs
- **Architectural design** = identify sub-systems and framework for control and communication; output = description of the software architecture. **Architecture in the small** (individual programs → components) vs **architecture in the large** (complex enterprise systems of systems, perhaps owned by different companies).
- Early stage; link between **specification and design**; often parallel with specification. Example: **packing robot control system**.
- Representation: simple **box-and-line diagrams** (abstract; good for stakeholder communication & planning; lack semantics) vs formal architectural models.
- **Advantages of explicit architecture:** stakeholder communication · system analysis (can it meet non-functional requirements?) · **large-scale reuse** (product-line architectures).
- **Fundamental questions:** generic architecture available? distribution? styles? structuring approach? decomposition into modules? control strategy? evaluation? documentation?
- **Architectural views – Kruchten's 4+1 model:** **Logical** (key abstractions as objects/classes) · **Process** (run-time interacting processes) · **Development** (decomposition for dev) · **Physical** (hardware & deployment) + **Scenarios (+1)** (use cases tying all views).
- **Architectural styles/patterns:** Layered, Client–Server, Repository (shared data), **MVC (Model–View–Controller)**, Pipe-and-Filter, Broker, Event-driven (publish–subscribe), **Microservices**, **SOA** (service-oriented), Monolith, Serverless, Peer-to-Peer, Hexagonal/Clean architecture, CQRS.
- **Monolith vs microservices:** microservices = small independent services, own DB, communicate by APIs/messages; scale independently; complexity in distributed systems.
- **API styles:** **REST** (HTTP verbs GET/POST/PUT/PATCH/DELETE, JSON), **SOAP** (XML), **GraphQL** (Facebook), **gRPC** (HTTP/2, protobuf), **WebSocket**, **webhooks**. **OpenAPI/Swagger**.

## Design patterns & implementation
- **Design process:** define context & modes of use → design system architecture → identify principal system objects → develop design models → specify object interfaces. **Build or buy?** Buying off-the-shelf is cheaper & faster; then design becomes *configuration*.
- **Design patterns:** from **Christopher Alexander** (1979, architecture); **Gang of Four (GoF)** book (Gamma, Helm, Johnson, Vlissides, 1994) – 23 patterns. Pattern elements: **Name · Problem description · Solution description · Consequences**.
  - **Creational:** Singleton, Factory Method, Abstract Factory, Builder, Prototype.
  - **Structural:** Adapter, Bridge, Composite, **Decorator** (extend functionality at run-time), **Façade** (tidy interface to related objects), Flyweight, Proxy.
  - **Behavioral:** **Observer** (notify objects of state change), **Iterator** (standard access to collection elements), Strategy, Command, State, Template Method, Mediator, Memento, Chain of Responsibility, Visitor, Interpreter.
- **SOLID** principles: **S**ingle Responsibility · **O**pen/Closed · **L**iskov Substitution · **I**nterface Segregation · **D**ependency Inversion. Others: **DRY**, **KISS**, **YAGNI**, separation of concerns, **high cohesion & low coupling**, Law of Demeter, composition over inheritance.
- **Implementation issues:** **Reuse** (levels: abstraction → object → component → system; reuse costs: finding & assessing, buying, adapting/configuring, integrating); **Configuration management** (versions, system building, change management, release management; supports integration so developers can access code in a controlled way); **Host–target development** (develop on a *host* platform/IDE, run on *target*; development vs execution platform; deployment factors: hardware/software dependency, availability across multiple platforms, communication traffic → co-locate chatty components).
- **IDE** = integrated tools: language-specific editor, compiler, debugger, graphical editing, testing, supporting tools. Examples: **Visual Studio**, VS Code, IntelliJ IDEA, PyCharm, Eclipse, Android Studio, Xcode, NetBeans.
- **Open source:** source published; volunteers contribute; **Free Software Foundation** (Richard Stallman, 1985; GNU). Business model: sell **support**, not software. **Licenses:** **GPL** (reciprocal/“copyleft”: derived works must be open source) · **LGPL** (link without publishing your component source) · **BSD** (non-reciprocal; may use in proprietary) · also MIT, Apache 2.0, MPL, Creative Commons. **Licensing management:** keep inventory, know license types, track evolution, educate, audit, participate.
- Generalization summary: design & implementation are interleaved; OO design includes architecture, identifying objects, design models (static: class/generalization/association; dynamic: sequence/state), component interfaces (UML `«interface»`).

## Integration & information systems · finals
### Organizational process
- Information system aligned with business process. **Bolman & Deal Four-Frame Model:** **Structural** (roles, controls, org charts) · **Human Resource** (needs of employees vs organization) · **Political** (individual/group interests, negotiation, power & conflict) · **Symbolic** (culture, rituals, stories).
- **Organization structures:** **Functional** (grouped by task/skills; quick decisions) · **Divisional** (branches/products; greater output of product variety) · **Matrix** (two ways: by function and by product team; more responsibility, innovative) · **Project-based** (teams by project need; common in IT solution companies).

### Methods of system integration
| Method | Key notes |
|---|---|
| **Horizontal** | chain of connected systems, **Enterprise Service Bus (ESB)**; subsystems comply with outside subjects |
| **Vertical** | operational level → management level (top-down / bottom-up pyramid); communication within the company; expensive for new functionality (needs new storage) |
| **Star** ("**spaghetti integration**") | each subsystem connected to multiple subsystems; e.g., m-commerce |
| **Common Data Format** | avoid converting to/from every other format; **Enterprise Application Integration (EAI)** middleware lets data flow without significant DB changes |
- **Advantages:** increased productivity, better management & analysis, lower costs, improved customer satisfaction. **Disadvantages:** security issues, complex upgrading.
- **System integration** = joining subsystems and ensuring they function as expected; connection of data, applications, **APIs** and devices across the IT organization.
- **System architecture** = conceptual structure, behaviors, dataflows and views of the system.

### Information system components
Hardware · Software · Database · Network · People (end-users; developers/admins) · Procedures. Types (TPS/MIS/DSS/EIS/ECS/PCS/TPS(Text Processing)/EDMS) → details in `02`.

## 3D texturing (Blender) · finals
- **Texture** = flat image applied to a 3D mesh for color/detail; **texturing**; texture artist. Texture affects the surface; material affects the object.
- **Types:** **Procedural** (nodes, math-defined, resolution-independent, Shader Editor) vs **Bitmap/Image texture** (needs **UV mapping**; JPEG/PNG/TGA).
- **UV mapping** = projecting 2D image onto 3D object (unwrapping); UV Editing workspace; **seams** (marked edges to limit stretching; Mark Seam via U key); unwrap methods: *Unwrap, Smart UV Project, Cube/Sphere/Cylinder projection, Project from View*. **Test grid** (checker image) detects distortion. **Texture paint**. **Baking** = pre-computing (shaders/lighting to image textures) to speed render; Cycles engine; pros: faster render, fewer polygons; cons: needs UV unwrap, large memory. Alternatives: **Substance Painter** (paid), Substance 3D Designer, Photoshop.
